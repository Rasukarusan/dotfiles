実装内容の説明 HTML を **単体ファイル 1 枚**として生成する。読み手はチーム全員 —
実装を知らないエンジニアと、非エンジニアの両方が同じ資料を読む。

## 禁止事項

- **Artifact にしない。** `Artifact` ツールを使わず、ファイルとして書き出す。共有するかは人間が決める。
- **ダークモード対応を書かない。** `prefers-color-scheme` も `data-theme` も使わず、`color-scheme: light` で固定する。
- **図なしでテーブル定義や処理を説明しない。** 表と文章だけの節は、読み手には「何の話か分からない塊」になる。
- **外部リソースを読み込まない。** CSS はインライン、図は SVG、フォントはシステムフォント。1 ファイルで完結させる。

## 出力先

チケットのドキュメントフォルダに **`explain.html`** という名前で保存する。ファイル名は固定。

フォルダの場所はグローバル設定の「md ファイルの出力先」ルールに従う
(ブランチ名から取ったチケット番号のフォルダ)。同じチケットのフォルダが既にあれば、その命名に合わせる。

scratchpad や `/tmp` には書かない (資料は関連ドキュメントと同じ場所に残す)。

## 手順

### 1. 材料を集める

- ブランチ固有のコミットを特定する: `git log --oneline $(git merge-base main HEAD)..HEAD`。
  親ブランチが main でないことがあるので、`git branch -a --contains <commit>` で分岐元を確かめる
- コミットメッセージ本文を読む (`git show --stat`)。**設計判断の理由はここに一番濃く書かれている**
- チケットのドキュメントフォルダにある plan.md・handoff.md・review-log.md を読む。
  review-log.md には「意図的に別 PR へ送ったもの」が載っているので、スコープ節の材料になる
- PR があれば `gh pr view`。無ければコミットから組み立てる
- 数値 (差分行数・テスト件数) は**その場で確認したものだけ書く**。古いメモの数字を転記しない

### 2. 構成を決める — 大きい話から小さい話へ

読み手は上から読む。**アーキテクチャに影響する変更ほど前**に置く。

1. **ヘッダー + 概要** — 3 行。この資料で一番読まれる場所
2. **登場人物** — 誰が出てくるか
3. **データモデルの変更 (DB)** — 構造が変わる話は最上位
4. **インフラ・env の変更** — 運用が変わる話
5. **設計判断** — なぜそうしたか
6. **処理の流れ** — 具体的な動き
7. **特に説明が要る仕組み** — 並行性・失敗時の挙動など、前提を知らないと読めないもの
8. **新しく入ったライブラリ** — **外部パッケージを新しく追加したときだけ書く**。
   自作のモジュール・共通処理は対象外 (それは他の節で説明する)。
   既存ライブラリの使い方が増えただけのものも書かない。外部パッケージの追加が無ければこの節は丸ごと落とす

不要な節は落とす。無理に埋めない。
**この一覧の名前をそのまま見出しにする。** 説明を足したくなっても見出しには付けず、節の最初の 1 文で言う。

### 3. 書く

`template.html` (このスキルと同じディレクトリ) の CSS とマークアップ例を土台にする。
CSS はそのまま流用してよい。

## 書き方の型

**この資料は実装の記録ではなく、チームが読むための説明**。密度を上げるほど良くなるものではない。
深さは図と実データで出す。文章は薄く、粒を揃えて置く。

### 文章の粒度

- **見出しは短い名詞句にする。** `—` や `:` で 2 つの主張をつながない。識別子・記号を入れない。
  - 悪い: `DB の変更 — 「どのブラウザのセッションか」を持つ` / `失効の届け方 — 配って回らず、中央で消す`
  - 良い: `データモデルの変更` / `失効の届け方`
  - 見出しで言いたくなった主張は、その節の最初の 1 文で言う
- **1 段落 1 主張、120 字まで。** 3 文を超えたら段落を割るか、図・表に置き換える。
- **1 つの節に段落を 4 つ以上積まない。** 積みたくなったら h3 で切る。切れないなら、その節は
  1 つの節に収まらない話を詰め込んでいる
- **段落の長さを揃える。** 250 字の塊と一行の段落が混在すると、どこを読めばいいか分からなくなる
- **実装の理由は「設計判断」の節にまとめる。** 他の節に「なぜこう書いたか」「代わりにこうもできたが」
  「E2E で踏んだ」を漏らさない。他の節は**何がどうなるか**だけを書く

### 言葉を選ぶ

- **識別子ではなく役割の名前で呼ぶ。** 関数名・テーブル名・env 名・SQL や Redis のコマンドは、
  読み手がその名前で grep する必要があるときだけ書く。
  - 悪い: 「署名付き browser_id cookie で引く対応表 browser_logins」
  - 良い: 「ブラウザを見分ける長寿命の cookie と、それに紐づくログインの対応表」
- 平易な言葉で一度定義した用語は、**最後まで同じ言葉で呼ぶ**。言い換えを増やさない
- 本文の `<code>` は 1 節あたり数個まで。表・図・コードブロックの中は制限しない
- 文体を通して揃える (常体・現在形・言い切り)。節ごとに語り口を変えない

### 概要は「技術記述＝意味」で書く

技術的に何をしたかと、それが何を意味するかを `＝` で結ぶ。技術記述は薄いグレー、
`＝` 以降は濃い太字で改行して出るので、**技術記述を読み飛ばしても意味だけ追える**。

```html
<li>
  【技術記述: 1 文。名前 (テーブル名・関数名・ファイル名) は 1 つまで入れてよい】
  <span class="mean">【それによって利用者・運用者から見て何が変わったか】</span>
</li>
```

**1 行 1 主張、`＝` の左右ともに 1 文。** 左側は 40 字程度まで。行の長さを揃えて、
6 行以上並べない。左側に識別子を並べない (1 行に 1 つまで、無くてもよい)。

- 悪い: 「/oauth2/end-session の after hook で、各プロダクトの Redis エントリ・登録簿 active_sessions の行・
  認可サーバー自身の session 行をまとめて削除する」
- 良い: 「ログアウトの終端で、そのブラウザのセッションを中央からまとめて消す」

`＝` の右側は**画面の向こう側にいる人から見て何が変わったか**を書く。実装の言い換えにしない。

- 良い: 「これまでは誰でも叩けた」「同時に操作しても勝手にログアウトされなくなった」
  「設定を変えた瞬間に反映される。反映待ちが無くなった」
- 悪い: 「guard を追加した」「排他制御を入れた」(技術記述の繰り返し)

数字が言えるなら入れる (「最大 15 分で反映される」「待ちは 5 秒で打ち切る」)。
挙動の変化は幅が伝わって初めて意味を持つ。

### 登場人物は主役と脇役を分ける

全部を同じ濃度で並べると、どこを見ればいいか分からない。

- **主役** (今回コードが大きく変わったもの): 青枠・大きめ。カードの下部に点線で区切って「今回」欄を作り、
  そこにも `＝` 形式で「何をした ＝ どういう意味か」を入れる
- **脇役** (既存のまま / 使い方が増えただけ): グレー・小さめ

見出しで「ここだけ押さえれば読める」と明示する。

### 図を先に決める

節を書く前に「この節は何の図で説明するか」を決める。図が思いつかない節は、
たいてい説明の粒度が間違っている。

| 説明したいこと | 使う図 |
|---|---|
| 2 つの条件の重なり・集合の関係 | ベン図 |
| テーブルどうしの関係 | ER 図。**新規は色付き / 既存はグレー + 凡例**で、今回足したものが一目で分かるようにする |
| データが何を意味するか | 実データのミニテーブル 3 枚 (入力 2 つ → 結果 1 つ) を横並び。seed の実際の値を使う |
| サービス間の処理の流れ | シーケンス図 (ライフライン + 番号付きメッセージ + note) |
| 並行処理・競合 | 2 レーンのタイムライン。**before (事故る) / after (直った)** を上下に並べる |
| 方式が変わった | before / after の対比図 (鍵の配り方・通信経路など) |
| 最終的な出力 | JSON のコードブロック。重要な行だけ色を変える |

**DB は ER 図と実データの併用が要る。** テーブル定義の表だけでは、そのテーブルが何を表すのか伝わらない。
ER 図で「どこにぶら下がるか」を示し、実データで「だから誰が何を使えるのか」まで見せて、
最後にそれが API 応答や画面としてどう出るかで閉じる。

### SVG を書くときの注意

- `<defs>` の marker は **SVG ごとに定義**し、id を figure ごとに変える (`#arrow` / `#k-arrow`)
- CSS で `svg text { font-size: … }` を書かない。**属性の `font-size` より CSS が勝つ**ので、
  個別指定が全部潰れる。共通クラス (`.box-label` など) 側で持たせる
- 円や枠の内側にテキストを置くときは、テキストの**左右の広がり**を見込んで座標を決める
- 横に広い図は `<div class="scroll">` で囲む (ページ本体が横スクロールしないように)

## 書き終えたら通しで見直す

書いた HTML を頭から読み、外れているものを直してから完成とする。

- 見出しに `—` や識別子が残っていないか
- 120 字を超えた段落、4 つ以上積んだ段落は無いか
- 概要が 1 行 1 文ずつで、行の長さが揃っているか
- 「なぜその実装なのか」が設計判断の節の外に漏れていないか
- 本文の `<code>` が多すぎないか。役割の名前で言い直せるものが残っていないか
- 通して読んで、文体と説明の高さが一定か

## 完成後

- ブラウザで開いて確認するようユーザーに伝える (`open <path>`)
- 資料に載せた注意点 (チケット番号のズレ、apply の順序、人間側の作業) は、
  本文に書くだけでなく**回答でも短く伝える**
