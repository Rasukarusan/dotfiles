ブランチの変更を **C4 モデルの図**で説明する HTML を**単体ファイル 1 枚**として生成する。
読み手は実装を知らないエンジニア。「システム全体のどこを触ったのか」を外側から順にズームして見せる。

## 禁止事項

- **Artifact にしない。** `Artifact` ツールを使わず、ファイルとして書き出す。共有するかは人間が決める。
- **ダークモード対応を書かない。** `prefers-color-scheme` も `data-theme` も使わず、`color-scheme: light` で固定する。
- **外部リソースを読み込まない。** Mermaid・PlantUML・C4-PlantUML の CDN も使わない。図はすべて手書きの インライン SVG、
  CSS はインライン、フォントはシステムフォント。1 ファイルで完結させる。
- **ブランチと無関係な要素で図を埋めない。** C4 は「全部を描く」図ではない。今回の変更を理解するのに要る要素だけ描く。
- **推測で要素を作らない。** コード・設定・インフラ定義で確認できたものだけを箱にする。

## 出力先

チケットのドキュメントフォルダに **`c4.html`** という名前で保存する。ファイル名は固定。

フォルダの場所はグローバル設定の「md ファイルの出力先」ルールに従う
(ブランチ名から取ったチケット番号のフォルダ)。同じチケットのフォルダが既にあれば、その命名に合わせる。

scratchpad や `/tmp` には書かない。

## C4 の 4 レベルとこの資料での扱い

| レベル | 何を描くか | この資料での扱い |
|---|---|---|
| 1. System Context | 利用者 (Person) と対象システム、外部システム | **必ず描く。** 変更が外から見えない場合も「どこの話か」の地図として置く |
| 2. Container | 対象システム内のデプロイ単位 (Web アプリ・API・ワーカー・DB・キュー・キャッシュ) | **必ず描く。** 変更があったコンテナを色で示す |
| 3. Component | 変更があったコンテナの中のモジュール・サービス・リポジトリ | **変更があったコンテナごとに描く。** 複数あれば h3 で分ける |
| 4. Code | クラス・型・テーブルの関係 | **構造の変更 (新しい型・テーブル・インターフェース) があったときだけ描く。** 無ければ節ごと落とす |

レベル間は**ズームの関係**にする。レベル 2 の図で色の付いたコンテナが、レベル 3 の図の外枠 (境界) になる。
各図の上に「前のレベルのどこを拡大したか」を 1 文で書く。

必要に応じて、レベル 3 の後に **Dynamic 図** (C4 の補助図: 番号付きの矢印で 1 つの処理の流れを示す) を置く。
新しい処理経路ができたときだけ使う。

## 色分けのルール

全レベル共通で、要素の状態を 4 色で示す。**どの図にも凡例を付ける。**

| 状態 | 見た目 | 意味 |
|---|---|---|
| 新規 | 緑の塗り + 太枠 | このブランチで新しく生まれた |
| 変更 | 青の塗り + 太枠 | 既にあり、このブランチで中身が変わった |
| 既存 | グレーの塗り + 細枠 | 変わっていないが、関係を説明するのに要る |
| 削除 | 赤の破線枠 + 打ち消し線 | このブランチで消えた |

矢印 (関係) も同じ色規則に従う。新しくできた依存は緑の矢印、消えた依存は赤の破線矢印。

## 手順

### 1. 材料を集める

- ブランチ固有のコミットを特定する: `git log --oneline $(git merge-base main HEAD)..HEAD`。
  親ブランチが main でないことがあるので、`git branch -a --contains <commit>` で分岐元を確かめる
- `git diff --stat <base>...HEAD` で変更ファイルを一覧し、**ファイルをコンテナに振り分ける**。
  振り分けの根拠はディレクトリ構成・`package.json` / `go.mod` などのモジュール境界・Dockerfile・
  docker-compose・Terraform / k8s マニフェスト・CI のデプロイ定義
- コミットメッセージ本文を読む (`git show --stat`)。設計判断の理由はここに一番濃い
- チケットのドキュメントフォルダの plan.md・handoff.md があれば読む
- PR があれば `gh pr view`

### 2. モデルを先に作る

HTML を書く前に、次の表を頭の中 (または scratchpad) で作る。図はこの表から起こす。

- 要素: 名前・種別 (Person / System / Container / Component / Code)・技術 (例: `Next.js`, `PostgreSQL`)・
  1 行の責務・状態 (新規 / 変更 / 既存 / 削除)・親要素
- 関係: 元 → 先・何をするか (動詞句)・プロトコル (HTTPS / gRPC / SQL / Pub/Sub など)・状態

**各要素の状態は diff で裏を取る。** 「変更」はそのコンテナ/コンポーネント配下にコード差分があるものだけ。

### 3. 構成

1. **ヘッダー + 概要** — 3 行の `＝` 形式 (技術記述 ＝ 意味)。概要の書き方は explain-html スキルと同じ
2. **System Context**
3. **Container**
4. **Component** — 変更コンテナごと
5. **Dynamic** — 新しい処理経路があるときだけ
6. **Code** — 構造の変更があるときだけ
7. **変更要素の一覧** — 図に出した新規・変更・削除の要素を表にまとめる (名前・レベル・状態・主なファイル)。
   ファイルパスを載せるのはこの表だけ

各図の節は「図 → 図の下に 2〜4 行の説明」の順にする。説明には**このレベルで何が変わったか**だけを書く。

### 4. 書く

`template.html` (このスキルと同じディレクトリ) の CSS と SVG の部品を土台にする。CSS はそのまま流用してよい。

## 図の描き方

- **箱の中身は C4 の表記に揃える。** 1 行目に名前 (太字)、2 行目に `[種別: 技術]`、3 行目以降に責務を 1 行。
  責務は 20 字程度まで
- **矢印には必ずラベルを付ける。** 「何をするか」を動詞句で。プロトコルは 2 行目に `[HTTPS]` のように小さく
- **境界は破線の角丸枠**で描き、左下に境界名を書く (`Clonos [Software System]` など)
- Person は円 (頭) + 角丸の胴体で描く
- 1 枚の図の要素は **10 個まで**。超えるなら既存要素を省くか、図を分ける
- レイアウトは**上から下へ**: 利用者 → 入口 (Web / API) → 内部 → データストア / 外部システム。
  外部システムは右端に寄せる
- 矢印同士・矢印と箱が重ならないように座標を決める。交差するなら箱の並びを変える

### SVG を書くときの注意

- `<defs>` の marker は **SVG ごとに定義**し、id を図ごとに変える (`#ctx-arrow` / `#cnt-arrow`)
- CSS で `svg text { font-size: … }` を書かない。属性の `font-size` より CSS が勝つので、共通クラス側で持たせる
- テキスト幅を見込んで箱の幅を決める。日本語は 1 文字 ≒ font-size 分の幅で見積もる
- 横に広い図は `<div class="scroll">` で囲む (ページ本体が横スクロールしないように)
- `viewBox` を付け、`width="100%"` で縮むようにする

## 文章の書き方

- 見出しは C4 のレベル名だけにする (`System Context` / `Container` / `Component: <コンテナ名>`)。主張は節の最初の 1 文で言う
- 1 段落 1 主張、120 字まで
- 識別子ではなく役割の名前で呼ぶ。図の箱の名前と本文の呼び方を一致させる
- 常体・現在形・言い切りで揃える

## 書き終えたら通しで見直す

- 全ての図に凡例があるか。色と状態の対応が全図で同じか
- レベル 2 で色の付いたコンテナが、すべてレベル 3 で拡大されているか
- 図の「新規・変更」と diff の中身が一致しているか (変更が無いのに青くしていないか)
- 矢印にラベルが無いもの、箱と重なっている矢印、はみ出したテキストが無いか
- 変更要素の一覧表と図の色分けが一致しているか
