ブランチの変更を **C4 モデルの図**で説明する HTML を**単体ファイル 1 枚**として生成する。
読み手は実装を知らないエンジニア。Context → Container → Component → Code の順にズームし、
「この PR が何を変えたか」を上から見せる。

## 禁止事項

- **Artifact にしない。** `Artifact` ツールを使わず、ファイルとして書き出す。共有するかは人間が決める。
- **ダークモード対応を書かない。** ライト固定。
- **外部リソースを読み込まない。** Mermaid・PlantUML の CDN も使わない。図はすべて手書きのインライン SVG、
  CSS はインライン、フォントはシステムフォント。1 ファイルで完結させる。
- **ブランチと無関係な要素で図を埋めない。** 今回の変更を理解するのに要る要素だけ描く。
- **推測で要素を作らない。** コード・設定・インフラ定義で確認できたものだけを箱にする。

## 出力先

チケットのドキュメントフォルダに **`c4.html`** という名前で保存する。ファイル名は固定。

フォルダの場所はグローバル設定の「md ファイルの出力先」ルールに従う
(ブランチ名から取ったチケット番号のフォルダ)。scratchpad や `/tmp` には書かない。

## 配色: 種類 × 状態

要素の**塗り**は C4 標準の種類の色、**今回の変更**は枠と文字色で重ねる。`template.html` の CSS 変数をそのまま使う。

| 種類 | 塗り |
|---|---|
| Person | `--person` (濃紺) |
| Software System (対象) | `--system` |
| Container | `--container` |
| Component | `--component` (薄青。文字は濃紺 `#0b2a4a`) |
| 外部システム | `--ext` (グレー) |

| 状態 | 描き方 |
|---|---|
| 新規 | 要素ごと緑で描く。Person・矢印は `--new` で塗る / 引く。Component は `--new-bg` の塗り + `--new` の太枠 + 名前に「(新規)」 |
| 変更 | 種類の塗りのまま、`--chg` (オレンジ) の太枠 (stroke-width 3〜4)。箱の最下行に**何を変えたか**を `#ffe0b2` (Component なら `--new` 等の濃い色) の太字で 1 行 |
| 既存 | 種類の塗りのみ、枠なし |

新しくできた経路は緑の破線矢印 + 緑の太字ラベル、変わった経路はオレンジの矢印 + オレンジの太字ラベル、
既存の経路はグレーの矢印 + グレーのラベル。凡例はページ冒頭に 1 つだけ置く。

## 構成

1. **h1** — `PR #<番号> <PR の内容を一文で>`
2. **サブ** — 「C4 モデル (Context → Container → Component → Code) で、この PR が何を変えたかを上から順に見る。」
3. **ひとことで** — カード 1 枚。2〜3 文で PR の要点を言い切る。必須になったもの・壊れる条件があればここで言う
4. **凡例** — 新しく足したもの / 変えたもの / 外部のシステム
5. **Level 1: System Context** `<small>誰が何とやりとりするか</small>` — 図 + 「外から見て何が増えたか」を 1 段落
6. **Level 2: Container** `<small>どの箱が何を持つか</small>` — 図 + **コンテナ × この PR で変えたこと**の表。
   変更なしのコンテナも最後の行に「変更なし」とまとめて書く。IAM などのインフラ定義の変更もここに行を足す
7. **Level 3: Component** `<small><コンテナ名> の中</small>` — 変更コンテナごとに図 + 「ポイント」の箇条書き
   (各項目は**太字の結論 1 文** + 理由 1〜2 文)。変更コンテナが複数あれば図と h3 を分ける
8. **Level 4: Code** `<small><何の形か></small>` — 下の「Code レベルの描き方」に従う
9. **リリース時に人がやること** — Terraform apply・データの配置・env の追加など、人の作業があるときだけ。
   `.warn` の囲みに番号付きで書き、**やらないと何が壊れるか**と**確認方法**を添える。無ければ節ごと落とす

## Code レベルの描き方

クラス図にこだわらない。**この PR で形が変わったもの**を、一番伝わる形で見せる。h3 で小分けにする。

| 変わったもの | 見せ方 |
|---|---|
| ファイル・オブジェクトストレージの置き場 | `<pre>` のツリー。新規は `<span class="n">`、補足は `<span class="c"># …</span>` |
| テーブル・型の関係 | ER 図 / クラス図の SVG。新規は緑枠 |
| 処理の順序・メッセージの並び | 番号付きの表。新規の行に `<span class="tag new">新規</span>` |
| プロンプト・JSON・設定の形 | `<pre>` に実物。新しい部分を `<span class="n">` で色付け |
| 条件ごとの振る舞い | 用途 × 条件のマトリクス表。セルに `tag new` / `tag chg` と、変更前の挙動を括弧で |

## 手順

### 1. 材料を集める

- ブランチ固有のコミットを特定する: `git log --oneline $(git merge-base main HEAD)..HEAD`。
  親ブランチが main でないことがあるので、`git branch -a --contains <commit>` で分岐元を確かめる
- `git diff --stat <base>...HEAD` で変更ファイルを一覧し、**ファイルをコンテナに振り分ける**。
  根拠はディレクトリ構成・モジュール境界 (`package.json` 等)・Dockerfile・Terraform / k8s マニフェスト・CI のデプロイ定義
- コミットメッセージ本文 (`git show --stat`) と PR 説明 (`gh pr view`) を読む。設計判断の理由とリリース手順はここにある
- チケットのドキュメントフォルダの plan.md・handoff.md・review-log.md があれば読む

### 2. モデルを先に作る

HTML を書く前に、要素 (名前・種類・技術・責務・状態・親) と関係 (元 → 先・何をするか・状態) を洗い出す。
**状態は diff で裏を取る。** 「変更」はその要素の配下にコード差分があるものだけ。

### 3. 書く

`template.html` (このスキルと同じディレクトリ) の CSS と SVG の部品を土台にする。CSS はそのまま流用する。

## 図の描き方

- 箱の中は 1 行目に名前 (太字)、2 行目に技術や責務、変更があれば最下行に「何を変えたか」
- **矢印には必ずラベルを付ける。** 動詞句か、プロトコル・API 名 (`HTTP` / `SQL (RLS)` / `Get + List`)
- 境界は破線の角丸枠、左上に境界名
- Person は円 (頭) + 角丸の胴体、データストアは円筒で描く
- Component 図はレイヤー (usecase / domain / infrastructure など) を**上から下の段**に並べ、段の左にレイヤー名を小さく書く
- 1 枚の図の要素は 12 個まで。矢印と箱・テキストが重ならないように座標を決める
- `<defs>` の marker は SVG ごとに定義し、id を図ごとに変える (`a` / `aN` → `b` / `bN` / `bC` …)
- 属性の `font-size` を潰さないよう、CSS で `svg text` に font-size を書かない (font-family だけ書く)
- 図は `<div class="card scroll">` で囲む

## 文章の書き方

- 識別子 (クラス名・パス・IAM アクション) は使ってよい。読み手が grep する前提の資料なので、本文中でも `<code>` で書く
- 1 段落 1 主張、120 字程度まで。表のセルも 2〜3 文まで
- 常体・現在形・言い切りで揃える

## 書き終えたら通しで見直す

- 図の色 (新規・変更) と diff の中身が一致しているか。Level 2 の表・Level 3 の図とも食い違っていないか
- Level 2 で変更にしたコンテナが、すべて Level 3 で拡大されているか (設定だけの変更コンテナは表だけでよい)
- 矢印にラベルが無いもの、箱と重なっている矢印、箱からはみ出したテキストが無いか
- リリース時の作業が PR 説明・コミットにあるのに、節が抜けていないか

- リリース時に人がやることがあれば、回答でも短く伝える
